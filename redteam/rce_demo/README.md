# Демо: RCE через Java-десериализацию

Наглядно показывает, ПОЧЕМУ `ObjectInputStream.readObject()` над данными от
клиента = удалённое выполнение кода (RCE), и как это закрыть.

⚠ Только для обучения/проверки своего сервера. Payload безобиден (создаёт файл
`PWNED.txt` и выполняет `id`) — это доказательство выполнения кода, не вред.

## Файлы
| Файл | Роль |
|---|---|
| `Evil.java` | обычный Serializable-объект; в `readObject()` — код «атакующего» |
| `VulnServer.java` | уязвимый сервер: `readObject()` из сети (как потенциально твой) |
| `SafeServer.java` | защищённый: белый список классов (`resolveClass`) |
| `Attacker.java` | шлёт сериализованный `Evil` на сервер |

## Запуск
```bash
javac *.java
# уязвимый
java VulnServer &              # порт 9970
java Attacker 9970             # → сервер выполняет id, создаёт PWNED.txt
# защищённый
java SafeServer &              # порт 9971
java Attacker 9971             # → ОТКЛОНЕНО, PWNED.txt не создан
```

## Вывод (проверено)
- Уязвимый: `СЕРВЕР ВЫПОЛНИЛ КОМАНДУ: id -> uid=0(root)...` + создан `PWNED.txt`.
- Защищённый: `ОТКЛОНЕНО -> заблокирован недопустимый класс: Evil`.

## Защита
1. Не десериализуй данные клиента через Java-сериализацию. Читай поля своего
   бинарного протокола вручную (int/string), без `readObject`.
2. Если иначе никак — белый список классов (`resolveClass`) или
   `ObjectInputFilter` (Java 9+).
3. Сервер — не от root, в песочнице/контейнере.

Связано: клиент TWWK использует `ObjectInputStream` (`J0/g.java`,
`x1/AbstractC0602a.java`). Проверь, не делает ли так же СЕРВЕР над вводом клиента.
