# Протокол TWWK — реверс-инженерная спецификация

Восстановлено статически из клиента (jadx). Это **настоящий** формат, на котором
игра общается с `twwk.ru`. Реализация — `redteam/twwk_protocol.py` (с самотестом).

Источники в коде:
| Класс | Роль |
|---|---|
| `y.AbstractC0612d`, `y.C0610b` | чтение из потока (reader) |
| `y.C0611c` | запись в поток (writer) |
| `J1.b.a()` | фабрика типов (тип-байт → класс) |
| `J1.b.d()/g()`, `e()/f()` | (де)сериализация значения |
| `i.g`, `i.c`, `k.e`, `k.b`, `k.h`, `w.d`, `r.c/r.d`, `u.d`, `x.b` | типы значений |

## Базовое

- Поток — `DataInputStream`/`DataOutputStream`, порядок байт **big-endian**.
- Транспорт — сырой TCP, **без TLS, без сжатия, без шифрования** (см. отчёт).

## varint (мелкое целое / длина) — `C0611c.d()` / `AbstractC0612d.b()`

Запись числа `v`:
| Условие | Байты |
|---|---|
| `0 ≤ v < 250` | 1 байт: `(v − 128)` |
| `250 ≤ v < 65536` | `0x7E`, затем int16 `(v − 32768)` |
| `v < 0` или `v ≥ 65536` | `0x7F`, затем int32 `v` |

Чтение: байт `rb`; `rb==126` → `int16 + 32768`; `rb==127` → `int32`; иначе `rb + 128`.
Байты `126/127` свободны как маркеры, т.к. однобайтовая ветка даёт максимум `121`.

## Строка — `C0611c.e()` / `C0610b.f()`

`varint(длина_в_символах)`, затем тело:
- **версия протокола ≤ 27:** 1 байт на символ, кодировка **Windows-1251**
  (кириллица А–я = `символ − 848`; Ё/Є/і/ї/ґ — спец-байты CP1251).
- **версия > 27:** UTF-16, 2 байта на символ (big-endian).

Длина `0` декодируется как `null` (пустая строка неотличима от null).

## Значение — `[1 байт тип][тело]`, тип `0` = null

Тип-байт структурирован: **`тип = (подтип << 3) | категория`** (младшие 3 бита — категория).

| Тип-байт | Категория/подтип | Класс | Тело |
|---|---|---|---|
| `0x00` | — | null | — |
| `0x09` | кат1 / 1 | `k.e` | **int32** (самый частый скаляр) |
| `0x31` | кат1 / 6 | `k.b` | **bool** (1 байт) |
| `0x17` | кат7 / 2 | `i.g` | **массив**: `int32 count`, затем `count` значений |
| (кат1) | — | `k.h` | **строка** (varint+CP1251) |
| (кат1) | — | `i.c` | **пара int32** |
| кат3 | — | `r.*`, `q.*`, `t.*` | игровые команды/операторы |

> Контейнер `i.g` использует **сырой int32** для счётчика (не varint) —
> подтверждено в `i.g.c()`: `c0610b.f5457a.readInt()`.

Полностью реализованы и проверены round-trip: null, int, bool, массив (в т.ч.
вложенный), строка CP1251, varint. Остальные листовые типы (`w.d`, `r.c/r.d`,
`u.d`, `x.b`) опознаются по тегу — их тела дочитываются по мере появления
реальных сырых кадров.

## Версии протокола

Байт версии (`C0610b.f5449b` / `C0611c.f5453b`) управляет кодировкой:
- `≥ 17` — включает таблицы шрифтов/фонов в потоке;
- `≥ 26` — добавляет 4-байтовый префикс длины секции ресурсов;
- `≤ 27` — строки в CP1251; `> 27` — строки в UTF-16.

## Конверт сообщения

В перехвате (`twwk_msg`) сообщение выглядит как `s=<секция> op=<операция> body=<тип>`:
- `s` — id секции/сервиса (165 различных),
- `op` — id операции (273 различных),
- `body` — сериализованное значение (по схеме выше) либо `null`.

### Каталог операций (из реального лога, 4311 сообщений)

| −2133443165 | 549 | null×549 |

| 216374679 | 240 | i.g×240 (массив) |

Операции с телом `i.g`/`k.e` несут изменяемое состояние — **именно их сервер
обязан валидировать сам** (см. `SERVER_HARDENING.md`). Операции с `null` —
пинги/подтверждения.

## Зачем это для защиты

Зная формат, ты видишь **каждое поле каждой команды**, которое приходит на
сервер. Правило прежнее: сервер не верит ни одному числу из клиента — он сам
считает результат. Этот кодек позволяет собрать корректный кадр и проверить,
проглотит ли сервер подделанное поле (а не только повтор сырых байт).
